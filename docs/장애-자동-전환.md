# PC 장애 시 클라우드 자동 전환

## 문제

온프레미스 앱의 공개 주소(`{app}.lilycloud.kr`)는 PC 터널을 가리키고, 버스팅 비율 분배도 PC 프록시가 한다.
PC 가 꺼지면 클라우드 대기 Pod 가 떠 있어도 서비스가 중단된다.

## 방식 비교

| 방식 | 장애 시 끊김 | 비율 분배 위치 | 비용 | 비고 |
|---|---|---|---|---|
| Cloudflare Load Balancing | 헬스 체크 주기 | 엣지 | 유료 애드온 (월 $5~, 오리진 수 비례) | 가장 깔끔하나 비용 |
| **CNAME 전환 (1단계, 채택)** | 유예 60초 + DNS 반영 | PC 프록시 (현행) | 없음 | 기존 자산으로 즉시 구현. Worker 의 예비 |
| **Cloudflare Workers (2단계, 재시도만 채택)** | 거의 없음 (요청 단위 재시도) | 엣지 (미구현, PC 프록시 그대로) | 무료 한도 (일 10만 요청) | LB 와 같은 재시도를 무료로 |
| 터널 커넥터 이중화 | - | - | 없음 | 미채택. 주/예비가 아니라 상시 분산되고, 에이전트마다 클러스터 커넥터·프록시 필요 |

## 1단계: CNAME 전환 (구현)

| 상황 | 동작 |
|---|---|
| 정상 | 공개 주소 → PC. 버스팅 비율 분배는 PC 프록시 (현행) |
| PC 장애 | 에이전트 연결이 끊긴 채 유예 시간이 지나면 builder 가 클라우드 레플리카를 올리고 Ready 확인 뒤 CNAME 을 ALB 로 전환 |
| 복구 | 에이전트가 다시 붙으면 CNAME 으로 거점(클라우드)을 복구. 사용자가 "내 PC 로 되돌리기"로 수동 복귀 |

- 대상: 끊기기 직전 상태가 버스팅 켜짐 · 대기 Pod 준비 · 거점 내 PC · DB 가 PC 에 없는 앱
- 구현: `AgentFailover` (끊김 감시·전환), `AgentHub` (끊긴 뒤에도 마지막 상태 보관), `AppAddress.pointCloud` (CNAME 변경)
- 설정: `FAILOVER_GRACE_SECONDS` (기본 60, 0 이면 끔), `FAILOVER_REPLICAS` (기본 2)
- 트레이드오프: 유예 시간과 DNS 반영 동안 서비스 중단. 정상 시 모든 요청이 PC 를 경유해 PC 가 진입 병목
- 실검증 (2026-10-02, airpointer-6f5a59): 에이전트 정지 63초 뒤 CNAME → ALB, 74초부터 공개 주소 200, 클라우드 레플리카 2/2

## 2단계: Cloudflare Workers (재시도 구현, 비율 분배는 미구현)

공개 주소 앞에 Worker `lily-edge` 를 두고, PC 가 응답하지 못한 요청을 엣지에서 클라우드로 다시 보낸다.

```
평소     {app}.{존} → Worker → CNAME 내용물(PC 터널) → 에이전트 프록시
PC 장애  {app}.{존} → Worker → 530·연결 실패·엣지 오류 페이지 → {app}-cloud.{존} → ALB → ingress-nginx → 클라우드 대기 Pod
```

| PC 쪽 결과 | 다시 보내는 메서드 | 이유 |
|---|---|---|
| 530 (터널 커넥터 없음), 연결 실패 | 모든 메서드 | PC 가 요청을 받지 못했다 |
| 엣지가 만든 502/503/504/52x 오류 페이지 (`/cdn-cgi/` 가 든 HTML) | GET/HEAD/OPTIONS | 터널은 붙어 있는데 PC 가 멈춤. PC 가 받았을 수 있어 POST 등은 두 번 처리되지 않게 그대로 돌려준다 |
| 응답 헤더가 1.5초 안에 안 옴 (#27 은 2.5초) | GET/HEAD/OPTIONS (SSE·WebSocket 제외) | 전원이 꺼진 PC 는 엣지가 터널이 끊긴 줄 몰라 6~14초 뒤에야 502 를 낸다 |
| 앱이 돌려준 5xx | 다시 보내지 않음 | 앱 응답이다 |

- 한 번 실패하면 10초 동안 PC 를 건너뛰고 바로 클라우드로 보낸다. 표시는 isolate 메모리와 Cache API(같은 데이터센터의 모든 isolate)에 둔다
- 1MB 를 넘거나 길이를 모르는 본문은 다시 보내지 않고 원래 오리진으로만 보낸다
- 클라우드로 보낸 요청에는 `X-Lily-Original-Host`, 응답에는 `X-Lily-Edge: cloud` 를 붙인다
- 1단계 CNAME 전환(`AgentFailover`)은 그대로 둔다. Worker 를 지나쳐도 60초 뒤에는 공개 주소가 ALB 로 바뀐다
- PC 프록시의 넘침 넘김·비율 분배는 그대로다

구현

- `src/main/resources/edge/worker.js`: Worker 스크립트
- `EdgeWorker`: builder 기동 때 스크립트 업로드. 대기 배포가 끝난 앱에 라우트 `{app}.{존}/*` 와 클라우드 주소 `{app}-cloud.{존}`(ALB 프록시 CNAME) 생성, 앱 삭제 때 둘 다 지움 (3단계부터 라우트는 온프레미스 배포가 끝나면 먼저 건다)
- 대기 배포 때 lily-cicd 에 `aliases: [{app}-cloud.{존}]` 를 보내 같은 `{app}-svc` 로 Ingress 규칙을 만든다
- `-cloud` 로 끝나는 앱 이름은 받지 않는다 (클라우드 주소와 겹침)
- 설정: `PLATFORM_EDGE_ENABLED` (기본 false, 꺼져 있으면 1단계만), `PLATFORM_EDGE_SCRIPT_NAME` (기본 `lily-edge`)
- 플랫폼 Cloudflare 토큰 권한: Workers Scripts:Edit (계정), Workers Routes:Edit (존)

- 앱별 비율을 Worker 가 읽을 곳(KV 등) 등록, 슬라이더가 그 값을 바꾸도록 변경

## 3단계: 엣지 읽기 사본 (Cache API)

DB 가 PC 에 있는 앱(`local`)은 클라우드 대기 Pod 도 역방향 터널로 PC DB 에 붙어 있어서, PC 가 꺼지면 대기 Pod 도 500 을 낸다.
대기 배포가 없는 앱(역방향 터널 없는 `local`, 온프레미스 전용)은 Worker 를 거치지도 않아 그대로 끊긴다.
그래서 PC 가 정상일 때 Worker 가 공개 GET 응답을 저장해 두고, 장애 때 그 사본으로 답한다.

```
평소     GET  → Worker → PC → 200 → 방문자 + (공개 응답이면) 이 데이터센터 Cache API 에 사본
PC 장애  GET  → Worker → PC ✕ → 클라우드 대기 Pod (없거나 5xx) → 사본 200, 없으면 503
         쓰기 → 지금과 같다 (사본으로 답하지 않는다)
```

저장소 비교

| 저장소 | 범위 | 반영 | 바깥에서 읽기 | 쓰기 한도 (무료) | 결정 |
|---|---|---|---|---|---|
| **Cache API** | 데이터센터 한 곳 | 즉시 (그곳만) | 없음 (그 존의 Worker 만) | 없음 | 채택. 추가 권한·바인딩·비용 없음, 잘못 저장돼도 피해가 데이터센터 한 곳에 머문다 |
| Workers KV | 전역 | 최대 약 60초 | 계정 토큰으로 읽기·목록 | 일 1,000회 | 전역 공유가 필요해지면 검토 |
| R2 | 전역 | 즉시 | 버킷 키로 읽기·목록 | 월 100만 회 | 2차 저장소 후보 (읽기 지연) |

저장 조건 (모두 만족할 때만, 공개 응답만 둔다)

- GET, 200, 요청에 `Cookie`·`Authorization`·`Upgrade` 없음
- 요청에 `X-Forwarded-Host`·`X-Original-URL` 등 앱이 응답 속 주소를 바꾸게 하는 헤더 없음 (사본 오염)
- 응답에 `Set-Cookie` 없음, `Cache-Control` 에 `private`·`no-store` 없음, `Vary` 는 `Accept-Encoding` 만
- HTML·JSON·CSS·JS·XML·이미지·폰트, 10MB 이하
- query 는 `page`·`p`·`sort`·`order`·`category`·`tag`·`q`·`lang`·`size`·`limit`·`offset`·`v`·`ver`·`version` 만. 이름순으로 키에 넣는다.
  `utm_*`·`fbclid`·`gclid`·`msclkid` 는 키에서 뺀다. 그 밖의 query(토큰 등)가 붙은 URL 은 저장도 조회도 하지 않는다

동작

- 키 `https://{host}/__lily_edge/snap{path}?{query}`, `Cache-Control: public, max-age=604800`(7일). 본문은 압축이 풀린 채 두고 `Content-Encoding`·`Content-Length`·`Set-Cookie`·`Vary`·`Age` 는 뺀다
- 사본 응답: 200, `X-Lily-Edge: snapshot`, `X-Lily-Snapshot-At`(저장 시각), `Cache-Control: no-store`. HEAD 는 본문 없이
- 장애 중에는 쿠키가 있는 GET 에도 공개 사본을 준다 (로그인 사용자는 로그아웃된 화면을 본다)
- 클라우드 대기 Pod 가 200 을 주면 사본보다 그 응답이 먼저다
- 사본이 있으면 클라우드 응답 헤더를 3초까지만 기다리고, 넘으면 사본으로 답하며 10초 동안 클라우드를 건너뛴다. DB 가 PC 에 있는 대기 Pod 는 PC 가 꺼지면 역방향 터널 너머 DB 를 기다리며 5xx 없이 멈춘다 (실검증에서 발견). 사본이 없으면 0 에서 올라오는 대기 Pod 를 위해 끝까지 기다린다
- 클라우드 주소가 없거나 닿지 않으면(이전에는 502) 503 `Retry-After: 30`
- PC 를 거친 PUT/PATCH/DELETE 가 2xx 면 그 경로(query 없는 키)의 사본을 이 데이터센터에서 지운다
- 저장·조회가 실패해도 원래 응답은 그대로 나간다

builder

- 온프레미스 배포가 SUCCEEDED 되면 `EdgeWorker.attachRoute` 가 라우트 `{app}.{존}/*` 만 건다 (클라우드 주소 레코드는 대기 배포 때 `attach`). 실패해도 배포는 성공이고 빌드 로그에 `edge: failed ...` 를 남긴다
- 이어서 `EdgePrewarm` 이 공개 주소를 쿠키 없이 연다: `/` → 그 HTML 의 같은 호스트 `href`·`src` → `/sitemap.xml` 의 `loc`, `/` 를 포함해 최대 50개. 결과는 빌드 로그 `prewarm: 12/14 pages 200 from https://...`
- 라우트 반영을 기다려 5초 뒤에 연다. 리다이렉트는 따라가지 않는다
- 앱을 지우면 라우트를 지우므로 그 호스트의 사본은 더 이상 쓰이지 않는다 (7일 뒤 만료)

한계

- 사본은 저장한 데이터센터에만 있다. 다른 데이터센터로 들어온 방문자(해외, 통신사에 따라 도쿄·홍콩)는 사본이 없다. prewarm 은 builder 가 있는 서울 리전에서 연다
- 자주 읽히지 않는 사본은 7일 전에 밀려날 수 있다
- 장애 중 읽기는 저장 시점 데이터다. 로그인 후 화면, 한 번도 열리지 않은 페이지, 쓰기는 제공하지 못한다
- PC 앱은 살아 있고 DB 만 죽어 앱이 5xx 를 주는 경우는 지금처럼 앱 응답을 그대로 준다 (PC 가 받지 못한 경우만 사본)
- 같은 이름의 앱을 지우고 다시 만들면 이전 앱의 사본이 7일 안에는 남아 있을 수 있다
- 장애 중 쓰기를 쌓았다가 복구 뒤 다시 보내는 것은 아직 없다 (Durable Object 큐로 계획)

## 공통 한계

- 클라우드 대기 Pod 가 있어야 넘길 수 있다 (버스팅이 켜진 앱). 대기 Pod 가 없으면 3단계 읽기 사본만 남는다
- DB 가 PC 에 있는 앱은 PC 장애 시 DB 도 함께 중단되어 이어받을 수 없다 (공개 GET 은 3단계 사본으로 답한다)
- 터널은 붙어 있는데 PC 가 멈춘 직후의 POST 등은 첫 요청이 오류로 끝난다 (다음 요청부터 10초 동안은 클라우드로)
