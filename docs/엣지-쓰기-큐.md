# 엣지 쓰기 큐 (Durable Object)

PC 가 꺼진 동안 앱 주인이 등록한 경로로 온 POST 를 Cloudflare 에 쌓았다가, PC 가 돌아오면 받은 순서대로 PC 에 다시 보낸다.
코드는 `src/main/resources/edge/queue.js`(Worker·DO), `EdgeQueue`·`EdgeQueueController`(builder), lily-frontend `WriteQueuePanel` 이다.

## 흐름

```
[평소]  POST /posts → Worker → 앱 DO(WriteQueue) → 큐가 비어 있으면 PC 로 바로 전달 → PC 응답
[장애]  POST /posts → Worker → 앱 DO → PC 가 받지 못함(530·연결 실패·PC 장애 표시) → SQLite 에 암호화 저장 → 202 + X-Lily-Queued-Id
[복구]  DO alarm(10초~60초) → GET / 로 PC 확인 → 쌓인 POST 를 순번대로 전송 → sent / failed
```

- 등록 경로의 POST 는 평소에도 DO 를 거친다. DO 가 요청을 하나씩 처리하므로 재전송 중에 들어온 POST 도 큐 뒤에 붙는다.
- 등록 경로는 `/posts` 처럼 적고, 그 아래(`/posts/3/comments`)도 맡는다. `/postsx` 는 맡지 않는다. 등록 경로 밖의 요청과 GET 은 지금과 같다.
- PC 에 보낸 뒤 엣지 오류(502 등)가 나면 바로 `GET /` 로 다시 확인한다. 확인도 엣지 오류면 PC 에 닿지 않으니 쌓고 202, PC 가 응답하면
  이번 요청만의 오류라 그대로 돌려준다. 터널이 끊긴 직후 1분쯤은 POST·GET 모두 502 Host Error, 그 뒤에는 530 이다 (E2E).
  PC 가 그 요청을 처리한 순간 죽었다면 재전송이 중복이 될 수 있다. 앱이 `Idempotency-Key` 를 보면 거를 수 있다.
- 장애를 한 번 보면 DO 가 장애 상태(`downSince`)를 기억한다. PC 확인이 성공할 때까지 새 POST 는 PC 에 보내지 않고 쌓는다.
  Worker 의 장애 표시는 10초 뒤 풀리지만 DO 의 장애 상태는 확인이 성공해야 풀린다. 큐가 비어 있어도 alarm 이 확인한다.
- 보내기 전 확인: `GET /` 가 5xx 거나 연결에 실패하면 보내지 않고 기다린다 (엣지 오류는 PC 에 닿지 않음, 앱 5xx 는 DB 가 아직 없음).
  앱의 `/` 가 늘 5xx 인 앱이 멈추지 않게, 엣지 오류가 아닌 5xx 가 10번 이어지면 보내 본다. 마지막 확인은 관리 상태 `lastCheck` 에 남는다.
  엣지 오류는 브라우저용 HTML(`/cdn-cgi/`)과 하위 요청용 텍스트(`error code: 1033`)를 모두 본다.
- 재전송 결과: 2xx·3xx → `sent`, 4xx → `failed`(다시 보내지 않음), 5xx·엣지 오류·10초 시간 초과 → 멈추고 다음 alarm 에 다시.
- 재전송 요청에는 `X-Lily-Replay: 1`, `X-Lily-Received-At`(원래 받은 시각), `Idempotency-Key`(요청에 없으면 큐 id)가 붙는다.
  시간 초과는 PC 가 받았는지 모르므로 같은 키로 다시 보낸다. 중복을 확실히 막으려면 앱이 `Idempotency-Key` 를 본다.
- 방문자는 `GET /__lily_edge/queued/{id}` 로 결과(`queued`·`sent`·`failed`, 상태 코드, 순번)를 본다.

## 배포 화면 체크박스

- 온프레미스 배포 확인 창의 `PC 장애 대비`: 장애 중 읽기 사본(Cache API), 장애 중 쓰기 보관(이 큐). 기본 둘 다 켜짐. 사용자는 켜고 끄기만 한다
- builder 가 배포 요청의 `edgeSnapshot`·`edgeQueue` 를 빌드 로그(`edgeSnapshot=on|off`, `edgeQueue=on|off`)로 남기고, 배포가 끝나면 앱 DO 설정에 넣는다. 쓰기 큐 켜기 = 등록 경로 `/` (모든 POST), 끄기 = 빈 목록. 읽기 사본 끄기 = DO 설정 `snapshot=false` → Worker 가 사본을 저장·응답하지 않고 prewarm 도 건너뛴다
- 값이 없는 요청(이 체크박스 전에 만든 프로젝트)은 앱의 지금 설정을 그대로 둔다. DO 설정에 `snapshot` 이 없으면 읽기 사본을 쓴다
- 큐가 비어 있고 장애가 아니면 POST 를 줄 세우지 않고 동시에 PC 로 보낸다. 쌓기와 재전송만 한 줄로 처리해 쌓인 요청의 순서는 지킨다

## 저장과 보안

- DO 하나가 앱 하나(공개 주소)다. SQLite 테이블 `q` 에 요청을, `config` 에 등록 경로를 둔다.
- 헤더(쿠키·인증 포함)·쿼리·본문은 `QUEUE_KEY` 로 AES-GCM 암호화하고, 행 id 를 추가 인증 데이터로 묶는다. 경로와 상태만 평문이다 (화면 목록).
- 앱당 1,000건, 본문 1 MiB 까지. 끝난 행은 7일 뒤 지운다. 앱을 지우면 `EdgeWorker.detach` 가 큐를 지운다.
- DO 가 PC 로 보내는 요청은 공개 주소를 거치므로 Worker 를 다시 탈 수 있다. `QUEUE_KEY` 로 만든 표시(`X-Lily-Edge-Queue`)가 맞으면 Worker 는 큐를 건너뛰고 오리진으로만 보낸다.

## 설정과 관리 주소

- builder `PLATFORM_EDGE_QUEUE_KEY` = base64 32바이트 (`openssl rand -base64 32`). 비우면 꺼지고 Worker 는 바인딩 없이 올라간다.
  바꾸면 쌓여 있던 요청을 풀지 못한다 (`failed` 로 남는다).
- 기동할 때 Worker 업로드에 DO 바인딩 `QUEUE`, 비밀값 `QUEUE_KEY`, `QUEUE_ADMIN_HOST` 를 넣는다. SQLite DO 마이그레이션 `lily-queue-v1` 은
  Worker 에 아직 없을 때만 보낸다. 바인딩을 넣은 업로드가 거절되면 바인딩 없이 다시 올린다 (PC 장애 재시도는 그대로 동작한다).
- 관리 주소 `lily-edge-queue.{zone}`: 프록시 AAAA `100::` 레코드와 Worker 라우트만 있다. 토큰은 `SHA-256("lily-edge-admin:" + QUEUE_KEY)`.

| builder | 관리 주소 |
| --- | --- |
| `GET /api/apps/{app}/write-queue` | `GET /apps/{app}.{zone}/queue` → `{paths, counts, items}` + builder 가 `routed` 를 붙인다 |
| `PUT /api/apps/{app}/write-queue` `{"paths": [...]}` | `PUT /apps/{app}.{zone}/queue/config` (빈 목록이면 끈다) |
| 앱 삭제 | `DELETE /apps/{app}.{zone}/queue` |

- Worker 는 앱의 등록 경로를 isolate 마다 30초 기억한다. 바꾼 경로는 다른 데이터센터에 최대 30초 늦게 닿는다.
- 요청이 Worker 를 거치려면 앱 공개 주소에 엣지 라우트가 있어야 한다 (`routed`). 온프레미스 배포가 끝나면 `EdgeWorker.attachRoute` 가 건다.

## 확인하지 못한 것

- 실제 Cloudflare 에서 DO 의 하위 요청이 앱 라우트를 다시 타는지 (타지 않아도 표시 헤더만 PC 로 가고 동작은 같다).
- Workers 스크립트 목록 API 의 `migration_tag` 로 마이그레이션 적용 여부를 판단한다. 필드가 없으면 보냈다가 거절될 때 빼고 다시 올린다.
